Iterations       : 100,000 per thread
Metric           : ops_per_sec  (total acquisitions / wall time)

Scenario
  2 shared locks. Each iteration a thread acquires whichever lock is free:
    1. pthread_mutex_trylock(lock[tid % 2])   — preferred lock (non-blocking)
    2. pthread_mutex_trylock(lock[1-tid%2])   — alternate lock (non-blocking)
    3. pthread_mutex_lock(lock[tid % 2])      — blocking fallback
  Allows up to 2 threads to proceed concurrently (one per lock).
  Differs from 1-lock high-contention: reduces serialization at the
  application level, so lockdep overhead is more visible in isolation.

Conditions
  baseline : no LD_PRELOAD
  lockdep  : LD_PRELOAD=./lockdep/liblockdep.so

lockdep limits (lockdep.h)
  LOCKDEP_MAX_LOCK_SLOTS      = 256
  LOCKDEP_MAX_HELD_LOCK_SLOTS = 64
  LOCKDEP_MAX_THREAD_SLOTS    = 128

--- What the Experiment Reveals ---

1. The per-thread RB implementation (f760bcd) reduces 2-lock any-acquire
   overhead from 3.4–5.4× to 1.3–1.9× across all thread counts. This is
   a 2–3× improvement in overhead ratio at every data point.

2. Lockdep throughput improved dramatically: at 8 threads, 2.4M → 7.1M
   ops/s (3.0× faster). At 64 threads, 2.1M → 6.3M ops/s (3.0× faster).
   The per-thread RB backend removes the g_meta_lock serialization that
   previously capped lockdep throughput at ~2-4M ops/s.

3. Lockdep throughput now stabilizes around 6-7M ops/s at ≥4 threads,
   compared to ~2M ops/s previously. The higher ceiling indicates that
   the per-thread architecture has shifted the bottleneck from metadata
   contention to application-level lock contention.

4. The overhead curve is now flat (1.3–1.9×) across 1–64 threads. The
   previous implementation showed degrading overhead at high thread counts
   (3.4× at 1 thread → 5.4× at 32 threads). The new implementation
   eliminates the thread-count-dependent overhead growth.

5. At 1 thread, lockdep throughput nearly doubled (17.7M → 34.9M ops/s),
   confirming reduced per-operation fixed cost even without contention.
